Why RRCF exists

Every robot has its own controller. That doesn't scale.

Robot deployment is heading toward billions of units across every morphology — nanorobots, agricultural swarms, industrial humanoids, home assistants, aerial and marine vehicles. Every one needs a human, or an AI acting on a human's behalf, in the loop: an operator, a supervisor, or someone who can hit the e-stop.

Today every robot ships its own bespoke controller and its own integration effort. RRCF is the missing operator layer in the robotics standards stack — it doesn't replace URDF/MJCF/SDF (physical description) or VDA 5050/Open-RMF (fleet mission assignment), it completes the stack above them.

RRCA, Adopters, and Adapters

RRCF separates the public operator contract from the code required to speak each vendor SDK, simulator API, ROS stack, serial protocol, or cloud robot API.

Adopter

A vendor, integrator, simulator provider, platform, or project that implements RRCF.

Adapter

Endpoint-specific bridge code mapping normalized controls, skills, and telemetry to the target SDK or API.

.rrcf.adptr

A ZIP-compatible Adapter package installed in addition to the vendor SDK. It is separate from the XML .rrcf declaration.

RRCA

The RRCF Robot Control Agent loads the declaration, selects a category module, verifies the Adapter, validates commands, and routes telemetry.

Robot or simulator

Adapter once per model or SDK family; generic controllers thereafter. Calibration, homing, and simulator tuning remain inside vendor firmware, the SDK, or the Adapter. RRCA does not define or parse a calibration record.

The standard

Five pillars

RRCF spans control, fleet coordination, integration, safety, and choreography — all from one declared file.

01

Remote Control

One unified operator UI for any robot, any morphology — rendered directly from the declaration. A model/SDK Adapter performs endpoint integration once, so controllers remain generic. Covers both live control and replay through the same declared interface.

02

Fleet Management

Complements VDA 5050 and Open-RMF rather than competing — RRCF sits above the mission-assignment layer.

03

Collection & Integration

The same wire format used for control doubles as the universal integration format for dashboards, time-series stores, digital twins, and imitation learning — every operator session is already a consistent-schema trajectory, ready to train on.

04

Safety

E-stop, watchdog timeout, geofence, and speed limits standardized across every robot, every morphology.

05

Choreography

.rrcm mission files for synchronized multi-robot operations — GPS clock-synced, pre-computed trajectories.

Morphology taxonomy

Twelve canonical categories

Every robot declares exactly one primary category, with capabilities layered on as attachments (arms, grippers, sensors, tools).

A category is not just a label — it decides which control axes and which telemetry fields the robot is required to declare. An aerial vehicle owes altitude and rssi; a fixed manipulator owes neither a locomotion axis nor a battery reading. The matrix is machine-readable and checked, not just documented.

The file format

A minimal .rrcf declaration

Morphology, skills, safety limits, and transport — all in one XML document that any compliant controller or VLA model can load at runtime.

<?xml version="1.0" encoding="UTF-8"?>
<rrcf version="1.0" xmlns="https://rrcf.io/schema/1.0">
  <meta>
    <name>Unitree Go2 + Z1 Arm</name>
    <vendor>Unitree Robotics</vendor>
    <physical_ref format="urdf" path="go2_z1.urdf"/>
  </meta>

  <primary category="legged">
    <locomotion axes="vx vy wz" max_vx="1.5" max_wz="2.0"/>
    <modes>stand trot bound crawl prone</modes>
  </primary>

  <skills>
    <skill id="sit" label="Sit" standard="true" cmd='{"mode":"sit"}'/>
    <!-- vendor-custom skill — VLA reads at runtime, no retraining -->
    <skill id="heel_stretch" label="Yoga Pose" cmd='{"mode":"custom_01"}'/>
  </skills>

  <!-- every field carries its own type, unit and range,
       so a controller can render it with no prior knowledge -->
  <telemetry>
    <field id="estop_state" type="boolean" widget="indicator"/>
    <field id="health" type="enum"
           values="ready degraded rejected fault estop disconnected"/>
    <field id="battery" type="number" unit="%" min="0" max="100" warn_below="20"/>
    <field id="speed" type="number" unit="m/s" min="0" max="1.5"/>
    <field id="temp" type="number" unit="degC" min="-20" max="100" warn_above="55"/>
  </telemetry>

  <safety>
    <estop required="true" topic="/rrcf/go2/estop"/>
    <watchdog timeout_ms="500" action="halt"/>
  </safety>

  <transport>
    <endpoint role="operator_cmd" protocol="rrcf_mqtt" topic="/rrcf/go2/cmd"/>
    <endpoint role="telemetry" protocol="mqtt" topic="/rrcf/go2/state" frequency_hz="10"/>
  </transport>
</rrcf>

Full annotated example with HUD, all five input modalities, and custom controls: see spec §7.1.

VLA integration

RAG for robots

A .rrcf file is designed to be loaded as context by a Vision-Language-Action model at session start — the same way a document is retrieved for RAG.

  • Declared skills extend the VLA's action vocabulary at runtime — no fine-tuning required.
  • Vendor-specific skills become available instantly, because the declaration is the context.
  • Generated commands are bounded by the declared safety limits.
  • The model reads observations the same way a dashboard does: every telemetry field arrives with its declared type, unit, and range, so battery: 18 is unambiguously 18% and 2 below the warning threshold — not a number needing a vendor lookup.
// every input modality produces the same
// normalized wire format command
{
  "rrcf": "1.0",
  "category": "legged",
  "lx": 0.75, "ly": 0.0,
  "rx": -0.25, "ry": 0.0,
  "mode": "trot",
  "skill": null,
  "estop": false,
  "input": "touch_web",
  "twist": {
    "linear":  {"x":0.75,"y":0.0,"z":0.0},
    "angular": {"x":0.0,"y":0.0,"z":-0.25}
  },
  "ts": 1719000000000
}
Command needs state

Nobody drives a car looking only at the road

You watch the speedometer, the fuel gauge, the temperature light. Take the dashboard out and you don't have a car that drives slightly worse — you have a car nobody should be driving, because the driver can no longer tell whether the last input did what they intended.

Commanding a robot is the same. estop:true is not a stop — it is a request to stop. Only estop_state coming back tells the operator the robot actually stopped. A command stream without a state stream is open-loop, and open-loop teleoperation of a physical machine isn't a reduced feature set. It's an unsafe one.

So telemetry isn't a bonus that falls out of the control format. It is the other half of the same contract, declared in the same file — and a declaration that omits a telemetry endpoint is rejected: 

$ rrcf-conformance lint no-telemetry-endpoint.rrcf
FAIL  no-telemetry-endpoint.rrcf
      ERROR schema [transport/endpoints]:
      A declaration with no telemetry endpoint is not
      safely commandable: an operator cannot be asked
      to command a robot whose current state they
      cannot see.
SELF-DESCRIPTION CONTRACT

A gauge is only useful if it's labelled

A speedometer works because the numbers mean km/h and the redline is marked — you don't need a manual. RRCF requires the same of every declared field: its own type, unit, and range. 

<field id="battery" type="number" unit="%"
       min="0" max="100" warn_below="20"
       label="Battery" widget="gauge"/>

A controller that has never heard of this robot can now draw the gauge, scale it correctly, and turn it amber at 20%. The moment a consumer has to know that this vendor's soc means battery percent, the operator layer has stopped being portable — and RRCF has no reason to exist.

Because command and state share one declared, self-describing schema, the things normally built per-vendor become build-once: fleet dashboards that render any morphology without per-robot config, one measurement schema in InfluxDB / TimescaleDB / Prometheus instead of one per vendor, generic pub/sub consumers on the declared <transport> endpoints, and imitation-learning trajectories that are already (state, action) pairs — because the state half was mandatory all along.

Recording & playback

rosbag / MCAP + Foxglove

If a robot's command and telemetry topics are already emitted in RRCF's wire format, recording them into an MCAP file (which natively supports arbitrary JSON-schema channels) is a real, concrete win today — not a hypothetical one.

  • One Foxglove layout, any robot. Build a layout once against the RRCF wire format and it works unmodified for a wheeled robot, a drone, or a humanoid — the generic Plot, Raw, and 3D panels read the declared units and ranges rather than needing a hand-built config per vendor.
  • Recordings are comparable across robots and vendors. A sit skill call or an estop:true event looks identical in the file whether it came from a Go2 or a Franka arm, so two fleets' logs can be diffed instead of translated.
  • A recorded session doubles as a conformance artifact. The same capture you opened in Foxglove is valid input to rrcf-conformance check-session — which is how a vendor proves the robot honours its declaration, not just that the file parses.
# buildable now, on top of what's already public —
# no new tooling required on either side

ros2 bag record /rrcf/go2/cmd /rrcf/go2/state

# open the result in Foxglove — the same layout
# works for /rrcf/drone_01/state, /rrcf/franka_arm/state,
# any RRCF-compliant robot

# and check the robot against its own declaration
rrcf-conformance check-session go2.rrcf session.jsonl
Adopter requirements

What it takes to interoperate

RRCF conformance covers the controller, RRCA runtime, and endpoint Adapter/robot boundaries. A human UI, fleet console, another robot, or VLA model sends the same declared contract; endpoint integration is implemented once in the compatible Adapter.

ROBOT

RRCF-compliant robot MUST

  • Expose a valid <rrcf version="1.0"> block, standalone or embedded in its description file.
  • Accept RRCF wire-format JSON on at least one declared transport endpoint.
  • Halt all motion immediately on estop:true — no exceptions.
  • Halt if no valid command arrives within the declared watchdog timeout.
  • Declare every telemetry field its category requires, and publish every declared field at ≥1 Hz.
  • Self-describe every field — type, unit, range — so a controller that has never seen the model can render it.
  • Publish estop_state and health, so an operator sees the robot's real state and not just their own last command.
  • Implement the e-stop in hardware, independent of the network link (spec §13).
CONTROLLER

RRCF-compliant controller MUST

  • Parse the .rrcf file standalone — no other description format required.
  • Render the core panel (joysticks, e-stop, speed, telemetry) for every category, without per-robot code.
  • Render category/skill/attachment-specific panels purely from the declaration.
  • Support touch_web as the baseline input modality.
  • Include rrcf, category, type, estop, and ts in every transmitted command — plus a Twist sub-object whenever the category declares locomotion axes (a bolted-down arm has no mobile base, so it isn't held to that rule).
  • Normalize all input axes to [-1.0, 1.0] in wire-format output.
  • Reject any command exceeding the robot's declared safety limits — applies equally to human input and VLA-generated commands.
RRCA + ADAPTER

Conforming deployment MUST

  • Load and validate the declaration before accepting commands.
  • Verify Adapter identity, compatibility, and package integrity.
  • Map required controls, skills, telemetry, and safe-state behavior.
  • Reject endpoint mismatches instead of silently claiming support.
  • Keep credentials and unit calibration outside public artifacts.

This split is what makes the three operator types — a human on a touchscreen, a fleet console commanding a robot on behalf of another robot, and a VLA model generating skill calls — fungible from the robot's point of view: all three speak the same wire format and are held to the same safety-limit contract, so the robot never needs to know which kind of operator it's talking to. Full requirements, including transport security and rate-limiting: spec §11–§13.

Enforcement

How “MUST” becomes more than a word

A requirement in a specification is unenforceable on its own. RRCF enforcement has three layers, and they check genuinely different things — which is why none of them replaces the others.

LayerWhat it checksHow
1 · Declaration The .rrcf declares everything its category requires, and every declared field self-describes rrcf-conformance lint
2 · Runtime The robot actually publishes what it declared, at the declared rate, inside the declared range rrcf-conformance check-session
3 · Certification The right to claim RRCF compliance in the market Foundation review — not yet operational

Layer 1 cannot tell a robot that publishes estop_state from one that merely promises to — that is exactly what layer 2 is for. And neither layer stops a vendor who simply never runs them; that gap closes only at layer 3, the same way USB-IF and the Wi-Fi Alliance close it, by controlling the compliance mark rather than the code. Being straight about it: layer 3 does not exist yet, so RRCF conformance today is self-asserted, and the Registry marks entries experimental until they publish evidence from layer 2.
