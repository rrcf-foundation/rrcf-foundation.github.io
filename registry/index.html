Portable runtime architecture

Adopter, Adapter, package, and Agent

Each term identifies a separate part of the ecosystem.

Adopter

A vendor, integrator, simulator provider, platform, or project that implements RRCF.

Adapter

Bridge code mapping normalized RRCF controls and telemetry to an SDK, simulator API, ROS, serial protocol, or cloud API.

.rrcf.adptr

A ZIP-compatible package containing the Adapter and manifest. It supplements the vendor SDK.

RRCA

The generic Agent that loads declarations, verifies Adapters, validates commands, and routes telemetry.

Discovery

How RRCA selects an Adapter

Registry matching narrows candidates; the Adapter must still probe the target and reject declaration or capability mismatches before actuation.

robot.rrcf + deployment identity
            |
            v
query configured Registry
            |
match model, RRCF, SDK/API, platform
and RRCA version for packages
            |
verify manifest + SHA-256 + trust policy
            |
probe -> initialize -> activate
For Adopters

Publish an Adapter

  1. Publish and version the model's XML .rrcf declaration, once rrcf-conformance lint passes with no errors.
  2. Implement one Adapter for the model or SDK family.
  3. Package it as <publisher>.<vendor>.<model>.<version>.rrcf.adptr.
  4. Declare compatibility for RRCF, RRCA, SDK/API, model, platform, capabilities, and applicable firmware.
  5. Submit a Registry pull request with license, provenance, digest, and conformance evidence.
EVIDENCE

What verified actually requires

A rrcf-conformance check-session report over a real capture from the target endpoint — not only a declaration that lints clean. A clean declaration proves the file is complete; it does not prove the robot honours it.

BOUNDARY

Calibration remains endpoint-specific

Vendor firmware, SDK code, or the Adapter owns calibration, homing, simulator gains, and tuning. RRCA does not parse a standardized calibration record.
