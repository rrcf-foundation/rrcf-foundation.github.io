Portable runtime architecture

Adopter, Adapter, package, and Agent

The terms identify different parts of the ecosystem and are not interchangeable.

Adopter

A vendor, integrator, simulator provider, platform, or project that implements RRCF.

Adapter

Bridge code mapping normalized RRCF controls and telemetry to a vendor SDK, simulator API, ROS, serial protocol, or cloud robot API.

.rrcf.adptr

A ZIP-compatible package containing the Adapter and manifest. It supplements the vendor SDK; it does not replace it.

RRCA

The RRCF Robot Control Agent: the generic runtime that loads declarations, verifies Adapters, validates commands, and routes telemetry.

How RRCA selects an Adapter

            |
            v
RRCA queries configured Registry
            |
            | match category, vendor/model, RRCF,
            | endpoint SDK/API version and target platform
            | plus RRCA version for installable packages
            v
verify manifest + package SHA-256 + trust policy
            |
            v
Adapter probe -> initialize -> activate
            |
            v
vendor SDK / simulator API / ROS / serial -> target

Registry matching is not a safety certificate for a physical unit. The Adapter still probes the target and must reject declaration or capability mismatches before actuation.

For Adopters

Publish an Adapter

  1. Publish and version the model's XML .rrcf declaration.
  2. Implement one Adapter for the model or SDK family.
  3. Package it as <publisher>.<vendor>.<model>.<version>.rrcf.adptr.
  4. Declare RRCF, RRCA, SDK/API, model, applicable endpoint firmware, category, platform, and capability compatibility.
  5. Submit a Registry pull request with license, provenance, package digest, and conformance evidence.
BOUNDARY

Calibration remains endpoint-specific

Vendor firmware, SDK code, or the Adapter owns calibration, homing, simulator gains, and tuning. RRCA does not parse a standardized calibration record. Registry metadata only declares which layer owns initialization.
