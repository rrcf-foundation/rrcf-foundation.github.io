Why convert instead of publishing the URDF/MJCF/SDF/USD directly?

A physical description file (URDF/MJCF/SDF/USD) typically encodes far more than a controller needs — exact link lengths, mass and inertia properties, gear ratios, and full collision/visual mesh geometry. That's often the part of a robot's design a vendor most wants to protect: it's close to a manufacturing blueprint, and it's frequently the input a competitor (or a training pipeline they don't control) would want most.

An .rrcf file only needs to declare the control surface: actuator/joint names and ranges, morphology category, skills, HUD fields, safety limits, and transport endpoints — the same information you'd normally hand a third-party integrator as API docs. None of that requires disclosing mass properties, precise link dimensions, or mesh data.

That makes "private physical file, public RRCF" a coherent, common pattern rather than an edge case — analogous to keeping a service's implementation private while publishing its OpenAPI/Swagger contract. Converting (rather than hand-authoring from scratch) just gives you a starting draft extracted from a file you already have, without redistributing that file itself. See the full breakdown in the adoption guide.

This tool only extracts what's mechanically inferable — it is not a substitute for authoring an accurate RRCF file. The converter can see actuator/joint names, ranges, and topology, but it cannot infer:

  • Skills — your actual named behaviors (e.g. heel_stretch, seed_row_align) and their command payloads. The output only stubs standard skills (stand/sit) where the category implies them.
  • Safety limits — your real e-stop topic, watchdog timeout, geofence, and speed limits. The draft ships placeholder values that will under- or over-constrain a real robot.
  • Transport credentials — your actual MQTT broker, topic namespace, or WebSocket port. Draft endpoints are placeholders.
  • Morphology category — guessed from joint-name heuristics (hip/knee/ankle → leg, shoulder/elbow/wrist → arm, wheel/steer → wheeled). Usually right for real robots, shakier for generic or test models — always confirm <primary category> by hand.
  • Which actuators matter operationally — custom_controls is capped at 5 by design (RRCF is an operator panel, not a raw joint-teleop protocol). High-DOF models will have unmapped actuators listed in a comment for you to fold into <skills> or a dedicated <attach> block.

Treat the output as scaffolding: fill in the TODO-marked skill, safety, and transport blocks, and eyeball the category guess, before this file drives an actual robot or is published for third-party integrators.
